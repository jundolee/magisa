# 사용 확대 전략

`/goal` 명령으로 "이걸 많이 쓸 수 있도록 전략을 작성하고 실행해달라"는 지시를 받고 작성/실행 중인 문서.
**해석**: "이걸" = 매기사(magisa) 서비스 자체. 최근 세션에서 로그인(Google OAuth 포함)을 도입하고 OAuth
브랜딩 심사(Search Console 도메인 인증 등)를 진행 중인 걸 보면, 이 서비스를 더 이상 "본인만 쓰는 도구"가
아니라 다른 사람도 로그인해서 쓰게 하려는 방향으로 보여서 이렇게 해석했다. 만약 의도가 다르면(예: 특정
기능 하나의 사용률을 올리는 것) 알려주면 방향을 바로 바꾼다.

## 현재 제품 구조가 growth 전략에 미치는 제약

- 글 목록(`/`)은 **모두에게 동일한 단일 큐레이션 피드**다. `sources`(구독 블로그 목록)는 관리자 1명만
  등록/삭제할 수 있고(`/sources`, `ADMIN_PASSWORD` 게이트), 로그인해도 자기만의 블로그 목록을 만들 수는
  없다 — 로그인의 효과는 "읽음/즐겨찾기 상태가 계정에 저장된다"는 것뿐(`docs/decisions.md` 2026-07-30,
  2026-08-13 참고).
- 클릭하면 원문(외부 사이트)으로 바로 이동한다 — 매기사 자체에 글 본문 페이지가 없다. 즉 매기사 도메인
  안에는 색인할 만한 고유 콘텐츠가 사실상 홈 화면 하나뿐이라, 검색엔진 SEO로 신규 방문자를 끌어오는
  효과는 원천적으로 작다(썸네일/요약만 있고 본문은 없음).
- 따라서 "사용 확대"는 **다중 사용자 소스 관리(멀티테넌시)로 제품을 바꾸는 것**이 아니라, 다음 두 가지에
  집중하는 게 현재 아키텍처와 가장 잘 맞는다:
  1. 지금의 큐레이션 결과를 더 많은 사람이 구독/공유하게 만들기 (배포·유통)
  2. 처음 오는 방문자가 로그인할 이유를 바로 알게 만들기 (온보딩 legibility)

멀티테넌시(사용자별 소스 목록)로 가는 옵션도 있지만 이건 스키마/쿼리 전면 재설계급 작업이라 별도로
논의하고 결정할 사안으로 남겨둔다(아래 "보류" 참고).

## 실행 항목

| 항목 | 상태 | 파일 |
|---|---|---|
| 자체 RSS 피드(`/feed.xml`) 공개 — 남들이 자기 리더로 이 큐레이션을 구독 | 완료 | `src/app/feed.xml/route.ts`, `src/app/layout.tsx`(alternate 링크) |
| 헤더에 RSS 구독 링크 노출 | 완료 | `src/components/page-header.tsx` |
| 처음 온 방문자용 한 줄 소개 + 로그인 가치 설명 | 완료 | `src/app/page.tsx` |
| "블로그 추천하기" 공개 제안 폼 — 소스 등록 권한은 안 열되, 추천은 누구나 | 완료 | `src/app/suggest/*`, `src/lib/data/source-suggestions.ts`, `supabase/migrations/0010_source_suggestions.sql` |
| 관리자가 추천 목록을 `/sources`에서 검토/처리 | 완료 | `src/app/sources/page.tsx`, `src/app/sources/actions.ts` |
| `/suggest`를 sitemap에 포함 | 완료 | `src/app/sitemap.ts` |
| 이메일 일일 다이제스트 (로드맵에 이미 있던 항목 — 재방문·공유를 유도하는 가장 강한 레버) | 보류 | 발신 인프라(Resend 등) 결정 필요, 별도 작업으로 진행 권장 |
| 랜딩/소개 페이지를 홈과 분리해 SEO 타이틀·구조화 데이터 보강 | 제안 | — |
| OG 이미지(사이트 대표 이미지) 생성 — 카톡/슬랙 공유 시 미리보기 품질 | 제안 | — |

## 적용/배포 필요 사항 (사용자가 직접 진행)

- `supabase/migrations/0010_source_suggestions.sql`은 이 세션의 Supabase CLI가 로그인돼 있지 않아
  원격 DB에 자동으로 적용하지 못했다. `supabase login` 후 `supabase db push`(또는 Supabase Dashboard
  SQL Editor에서 직접 실행)로 적용해야 `/suggest` 폼이 실제로 동작한다. 적용 전에는 제안 제출 시
  `source_suggestions` 테이블이 없다는 에러가 난다.

## 보류: 멀티테넌시(사용자별 소스 목록)

로그인한 사용자가 각자 자기 블로그 목록을 관리하게 하려면 `sources.user_id`(이미 nullable 컬럼으로
존재, 2026-07-28 결정 참고)를 실제로 채우고, 글 목록/수집 파이프라인을 사용자별로 분리해야 한다. 이건
"성장 전략 실행" 범위를 넘어서는 제품 방향 결정이라 이번엔 진행하지 않았다 — 필요하면 별도로 논의.
